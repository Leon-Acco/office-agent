一、产品是什么

Office_Agent 是一个「多 Agent 虚拟办公室」：把一家公司的组织结构搬进浏览器，用 AI 员工承接「找人问」这个过程。

产品的核心隐喻是组织，而不是聊天框。

用户不需要知道「该问谁」，像在真实公司里那样走到总前台提问即可，系统自动分诊到对口的 AI 员工；跨领域的复杂问题进入协作会议室，由多个 AI 员工并行产出、互评、合成一份完整方案。

二、要解决什么问题

🎯

企业知识散落在代码仓库、文档和资深员工的经验里。通用 AI 助手不了解具体代码库与业务规范，答案不可信；而一个大而全的「企业助手」又容易因为上下文过载、权限不清、责任无人承担而失控。Office_Agent 走的是第三条路：按组织切分责任与边界。

现实痛点传统做法的局限Office_Agent 的解法
新人不知道该问谁、资深员工被反复打扰靠 IM 群里 @ 人，响应慢、重复劳动总前台三级分诊，自动路由到对口领域员工
通用 AI 不懂自家代码与业务只能给通用答案，容易一本正经胡说员工绑定具体 Git 仓库 + 已审核知识库，强制「先查后答」
单一助手上下文爆炸、能力边界模糊一个 prompt 塞满全公司知识，效果反而变差按领域切分员工，每个员工只挂自己的仓库/知识/技能/工具
AI 乱调工具、越权访问、泄露密钥无审计、无边界岗位包工具白名单 + 只读模式 + 注入防护 + 结果脱敏 + 审计日志
跨部门问题没人能一次答全需要拉会、串行沟通协作会议室：并行草案 → 互评 → 合成方案，冲突显式标注
AI 答案无来源、无法沉淀一次性对话，知识不复用知识候选审核状态机，审核通过才进检索
AI 配置随意改、上线无管控改 prompt 就上线，出事无法回滚岗位包版本状态机 + 变更审批单 + 灰度发布 + 回滚

4.3 AI 员工的五部分装配

员工能力全部在后台配置，不需要改代码：

  1. 身份：姓名、职位、Emoji、所属部门与领域、职责描述
  2. 行为准则（AGENTS.md）：员工级人格与边界指令
  3. 技能包（Skills）：可复用的执行规范；prompt 里只放摘要，需要时由 AI 调 loadSkill 取全文
  4. 资源绑定：绑定的 Git 仓库（检索自动限定在该范围）、已上传文档、知识库领域
  5. 岗位包（RolePack）：工具白名单 + 只读权限 + 执行预算（步数/调用数/超时/Token）

4.5 协作会议室

🤝

设计目标不是「多个 AI 各说各话」，而是模拟一场真实的评审会：不追求共识，而是保留分歧。

合成文档固定六个章节：任务背景与目标 / 总体方案 / 各部门要点与衔接 / 分歧点与裁决 / 风险与待确认 / 行动清单与分工。任务卡首行以 ✅ 或 ⚠️ 标记是否存在未解决冲突。

时间预算自动切分，任何一环超时都有兜底：草案保留、状态回退、代码拼接生成汇编版方案。

4.6 治理与安全能力

能力说明
岗位包版本状态机DRAFT → IN_REVIEW → CANARY → RELEASED → RETIRED，支持灰度百分比与回滚
变更审批引擎单人 / 双人 / 法定人数三种审批策略，覆盖岗位包、工具、技能、策略、知识
策略中心ACL / 脱敏 / 预算 / 工具风险四类规则，版本化可回溯
治理角色平台管理员、岗位包 Owner、知识审核员、安全审核员、审计员
知识审核流SUBMITTED → IN_REVIEW → APPROVED / REJECTED → EXPIRED，只有 APPROVED 参与检索
运行时防护参数注入检测、结果脱敏（password/token/key 等）、审计日志
执行预算每次对话限制推理步数、工具调用次数、超时与 Token

需要说明的是，注入检测目前是英文关键词黑名单，不应被视为安全边界，其主要价值是审计留痕。真正的边界是工具白名单与仓库作用域——它们在代码执行层生效，不依赖模型自觉。

五、产品价值总结

维度价值
效率问题自动路由，无需人工找人；原本要拉会讨论的跨部门问题，一次任务即可拿到一份带分歧标注的初稿
可信强制先查后答，答案基于真实代码与已审核知识；查不到时明确回复「未找到」
可控工具白名单 + 只读模式 + 预算上限 + 审计日志，AI 的能力边界由配置决定
可演进新增一个员工 = 后台配置（选领域、绑仓库、挂技能、配工具），不需要发版
可沉淀对话结论可提交为知识候选，审核后成为全公司可检索资产

六、当前边界与已知限制

⚠️

以下为对当前代码快照的客观盘点，直接影响能否投入生产。

  1. 检索是关键词匹配，不是向量语义检索。知识库检索为「先取最近 5 条 → 再做子串过滤」，代码检索为逐行 grep。其中「先取 5 条再过滤」属于逻辑顺序缺陷而非取舍，会导致超出 5 条范围的知识永远无法召回，是优先级最高的修复项。
  2. 无用户体系。会话统一挂在 guest 用户下，登录与多租户尚未落地，治理角色也未落到具体人头。
  3. 配置默认值含明文凭据。config.py 中 MySQL / Redis / LLM Key 存在硬编码默认值，且仓库公开，这三项应视为已泄露，需轮换并改为强制环境变量注入。
  4. 强依赖单一模型。默认智谱 GLM-5.2（Anthropic 兼容端点），并发闸默认仅 2。低并发是为规避限流的主动选择，但同时制约了协作会议室的真实并行度。
  5. 仓库存放于本机文件系统。Git 仓库 clone 到 workspaces/，横向扩容需共享存储；部分 git 命令为同步调用，会阻塞事件循环。
  6. 前端为无构建原生 SPA。修改 JS 需手动 bump ?v=N 破坏缓存；项目回滚依赖 .bak 备份链而非 Git。

七、计划

  1. 修复知识检索的过滤顺序，并引入向量检索做混合召回（对答案质量提升最大）
  2. 补齐用户体系与按人的 ACL，使「只读 / 可写」真正落到具体账号
  3. 将「对话结论一键提交为知识候选」做成前台按钮，闭环知识沉淀
  4. 协作会议室增加实时进度流（当前为轮询），使评审过程可观测
  5. 将采纳率、工具命中率、分诊准确率做成可观测看板，驱动员工配置迭代
